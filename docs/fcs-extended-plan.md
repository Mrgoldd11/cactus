## 1. Зачем это нужно

**Что такое FCS Extended.** Чужой проект ([BFrizzleFoShizzle/FCS_extended](https://github.com/BFrizzleFoShizzle/FCS_extended),
GPL-3.0, Nexus mods/1825). Это запускалка для настоящего FCS: её кладут в папку игры и запускают
вместо FCS. Она на лету патчит FCS (Harmony) и подгружает расширения из папок модов.

**Кому и зачем это нужно.** Игра сама по себе не умеет того, что умеют плагины RE_Kenshi
(например, переменные мира, новые условия диалогов, «тихие» состояния мира). Чтобы автор мода мог
редактировать такие данные в FCS, плагин вместе со своим модом кладёт в папку:
- `fcs.def` — новые типы записей, поля, значения enum'ов, пункты дерева категорий;
- иногда `*.def.patch` — правки ванильных `.def`;
- иногда DLL-плагин для самого FCS.

Без этого в FCS новые поля невидимы. В Cactus ситуация та же: данные не теряются (запись байт в
байт, неизвестные поля достраиваются из данных — `withInferredFields`), но поля показываются без
имени, без описания и без правильного вида; новые типы записей называются `TYPE_900`; новые
значения enum'ов — просто числа.

**Насколько это востребовано — честно.** Таких модов мало и они узкие (плагины RE_Kenshi). Среди
105 установленных у автора модов нет ни одного с такими файлами. Приоритет B (в
`fcs-comparison.md` строка 19). Зато это дёшево и это вопрос «настоящая замена FCS»: автор
RE_Kenshi-плагина кладёт один `fcs.def` в мод, и он должен работать и в FCS Extended, и в Cactus.
Ничего своего не изобретаем — берём их формат как есть.

## 2. Цели (в порядке важности)

1. **Совместимость.** Всё, что FCS Extended делает с defs, Cactus делает так же и даёт тот же
   результат: тот же порядок загрузки, те же правила слияния, тот же формат файлов. Мод,
   собранный под FCS Extended, в Cactus открывается с теми же типами, полями и enum'ами.
2. **Оптимизация и аккуратная архитектура сразу.** Это глобальная вещь (схема нужна везде: ядро,
   MCP, CLI, окно). Поэтому без временных глобалов и костылей, с кэшем, с тестами.
3. **Прозрачность.** Пользователь видит, что именно подгружено и откуда (окно «Расширения мода»).

Не цель: запускать DLL-плагины (они .NET и привязаны к внутренностям FCS), запускать сам FCS
Extended, писать свой формат.

## 3. Как работает FCS Extended (сверено с исходниками `Program.cs`)

| Что | Как |
|---|---|
| Что считается расширением | папка мода (`mods/*` и папки мастерской) с `FCS_extended.json`, `fcs.def`, `fcs_preload.def` или `*.def.patch` |
| Порядок обхода папок | сначала подпапки `mods/` (порядок `EnumerateDirectories`), затем папки мастерской |
| Включение | галочки в окне запуска, сохраняются в `%AppData%` (`FCS_extended.json` в `UserAppDataPath`). Новые расширения включены по умолчанию |
| `fcs_preload.def` | читается **до** ванильных defs (в первый вызов `Definitions.Load`) |
| `fcs.def` расширения | читается **после** ванильных (на загрузке `settings.def`, это последний) |
| `*.def.patch` | имя `X.def.patch` правит файл `X.def` по имени. Формат: пары строк «регулярка» / «замена»; чтение до первой пустой строки; если у регулярки нет строки замены — замена пустая. Применяется к тексту `.def` до разбора. Движок регулярок .NET. Патчи от разных расширений накапливаются по порядку обхода |
| Enum'ы | `enum X { ... }` в расширении **дописывает** значения в уже существующий enum (а не заменяет). Пустой `enum X { }` — сигнал «взять встроенные значения из FCS» (для Cactus это уже сделано через `builtin-enums.ts`) |
| Дерево категорий | секции `[FCS_LAYOUT]` из разных файлов **склеиваются** (вызов `clearCategories` отключён) |
| Новые типы записей | значения enum `itemType` (например `VARIABLE=900`) берутся из этого же слоя enum'ов; `[VARIABLE]` в `fcs.def` потом работает как обычная секция типа |
| DLL | `FCS_Plugins` в `FCS_extended.json` — список DLL с `IPlugin.Init(assembly)` |

Примеры для сверки лежат в `kenshi-bridge/_downloads/examples/` (`Dialogue/DialogueExtensions`,
`WorldStates/WorldStates`). `WorldStates/WorldStates/WorldStates.mod` — **настоящий мод** с
записями типа `VARIABLE` (900): готовый реальный тест на «открылось, имена видны, при сохранении
байты не изменились».

> **Поправка (2026-11-14).** `WorldStates.mod` (как и `DialogueExtensions.mod`) — это 46 байт, один
> заголовок, **записей в нём нет**. Он годится для проверки «мод открылся со своим расширением,
> тип 900 называется `VARIABLE`, поля с описаниями, запись байт в байт», а сами записи типа 900
> проверяются на своих фикстурах и созданием записи в тесте.

Что в них видно: `fcs.def` расширения — это **один файл, где смешаны** `enum`-блоки, секции типов
(`[VARIABLE]`, `[DIALOGUE,DIALOGUE_LINE,WORD_SWAPS]`) и `[FCS_LAYOUT]`. У нас сейчас три
отдельных парсера (`fcs-def.ts`, `fcs-enums.ts`, `fcs-layout.ts`) на три файла.
В одном из примеров файл назван `FCS.def` (регистр): сравнивать имена без учёта регистра.

## 4. Решения по архитектуре

### 4.1. Слои схемы вместо склейки текста
- Ваниль (`fcs.def`, `fcs_enums.def`, `fcs_layout.def`) разбирается **один раз** и кэшируется
  (не зависит от мода).
- Расширение разбирается **отдельно** и накладывается на разобранную схему (секции типов
  дописываются, enum'ы дописываются, layout склеивается), а не склеивается текстом с ванильным
  файлом. Так нет повторного разбора 100+ КБ ванильного defs при каждом открытии мода.
- Исключение: если у расширения есть `*.def.patch`, ванильный текст нужного файла патчится и
  разбирается заново (патч применяется к тексту, иначе никак). Это редкий случай, платим за него
  только тогда.
- Нужно проверить, что порядок «ваниль → расширения» даёт тот же результат, что склейка текстом
  (например, повтор поля с другим видом — предупреждение, как и сейчас).

### 4.2. Разбор «смешанного» файла
Расширенный `fcs.def` содержит и enum'ы, и секции типов, и `[FCS_LAYOUT]`. Нужна функция-разделитель
(`splitDefText`), которая разрезает такой текст на три части и отдаёт существующим трём парсерам,
сохраняя номера строк и имя файла-источника для предупреждений. Ванильные файлы идут тем же
путём. Новых парсеров не пишем, только разделитель. **Уточнить на реальных примерах** (оба
файла из `examples/`), как именно в них заданы значения `enum` и пустые enum'ы.

### 4.3. Новые типы записей: без глобального состояния
Сейчас `ITEM_TYPE_NAMES` — зашитая таблица, а `itemTypeName(n)` / `itemTypeId(name)` — глобальные
функции, их вызывают ~30 мест. Простой путь («глобальный реестр дополнительных типов») плох: два
мода с разными расширениями в одном процессе (MCP-сессия, тесты, будущие несколько окон)
перетрут друг друга.

Решение: таблица типов — **часть схемы** (`GameSchema.itemTypes`), ванильная таблица — значение
по умолчанию. В `ModContext` добавить метод `typeName(rec.type)`, который берёт таблицу из
схемы своего контекста. Места, где контекст есть, переводятся на него; остальные остаются на
ванильной таблице (для них неизвестный номер всё так же `TYPE_<n>`). Изменение механическое и
покрывается существующими тестами.
- `isItemTypeName` в `buildGameSchema` проверяет по таблице схемы, поэтому для зарегистрированных
  типов предупреждение «неизвестный тип записи» пропадает.
- **Проверить в первой же задаче:** где в настоящем расширении определён
  `enum itemType { VARIABLE=900 }`. В примере WorldStates он только в комментарии
  (`// enum itemType { VARIABLE=900 }`). FCS Extended берёт имена `itemType` из того же слоя enum'ов,
  значит в рабочем расширении строка должна быть настоящей — посмотреть исходники
  BFrizz_Extra_Extensions и KenshiLib_Examples. Если определения нигде нет — решить, как узнавать
  номер типа (например, из данных мода: `.mod` хранит только номера).
- **Сделано (этап 1), ответ на вопрос.** В настоящем расширении WorldStates числа 900 нет ни в
  одном def-файле как настоящего enum: в `FCS.def` только комментарий
  `// enum itemType { VARIABLE=900 }`, сам номер живёт в DLL-плагине. Cactus DLL не запускает,
  поэтому номер типа он узнаёт так (`resolveItemTypes` в `schema/game-schema.ts`):
  1. настоящий блок `enum itemType { ИМЯ=N }` в def-файле расширения — идёт в таблицу типов;
  2. если настоящего блока для этого имени нет — подсказка в комментарии
     `// enum itemType { ИМЯ=N }` (как у WorldStates);
  3. иначе тип остаётся без номера: предупреждение на английском с просьбой добавить такую
     строку, записи показываются как `TYPE_<n>`.

  Из данных мода номер **не** угадывается. Конфликты: имя встроенного типа с другим номером и
  номер встроенного типа — предупреждение, объявление пропускается; одно имя с двумя номерами —
  выигрывает последнее + предупреждение; один номер у двух имён — оба имени находятся, по номеру
  показывается последнее + предупреждение.
- **Сделано (этап 2).** `ModContext.typeName` / `typeId`; переведены вызовы в `model/`, `schema/`,
  `world/`, `format/helpers.ts`. Не переведены: `model/translate.ts` (там нет контекста, типы
  расширений в таблицах перевода видны как `TYPE_<n>`) и 37 вызовов `itemTypeName` в
  `apps/desktop` (это этап 4).

### 4.4. Кэш и скорость
- Ключ кэша расширенной схемы: список включённых расширений с `mtime`+`size` их файлов + то же
  для ванильных defs. Нет изменений — берём готовую схему (в MCP уже есть `schemaCache`, но он
  не зависит от мода; сделать зависимым).
- Поиск расширений — один проход по `mods/` и мастерской без чтения содержимого файлов, кроме
  небольших `FCS_extended.json`/`.def`. Мастерская большая (105 модов): не открывать `.mod`.
- Замер до/после на `pnpm bench` (`scripts/bench-load.ts` уже мерит загрузку схемы): открытие
  мода без расширений не должно стать медленнее.
- **Сделано (этап 3).** Кэш живёт в ядре (`node/schema.ts`, `loadGameSchema(paths, { extensions })`)
  и общий для MCP, CLI и скриптов: ванильные файлы разбираются один раз на все наборы расширений,
  готовая схема хранится по ключу «путь+размер+время каждого файла», до 8 наборов. Свой
  `schemaCache` в MCP убран: `session.schema()` — это схема открытого мода. Схема теперь общий
  объект, менять её на месте нельзя (сейчас никто и не меняет: `withInferredFields` делает копию).
  Замер на `mods/Cactus Info`, по три прогона: медиана открытия мода до — 26,3 / 28,2 / 23,7 мс,
  после — 15,7 / 17,5 / 15,4 мс (первое открытие в процессе 28–34 мс: оно разбирает схему). Поиск
  расширений для одного мода — около 0,06 мс; полный обход `mods/` и мастерской
  (`findExtensions`) — около 5 мс.

### 4.5. Какие расширения применять
- FCS Extended применяет **все включённые** сразу, независимо от открытого мода. Cactus
  по умолчанию применяет расширения **открытого мода и его зависимостей** (ему не нужны чужие
  поля от неподключённых модов, и схема остаётся минимальной). В окне — ручные галочки для
  остальных. Порядок слоёв: как у FCS Extended (папки `mods/`, затем мастерская), внутри
  зависимостей — по `data/mods.cfg`. Различие явно описать в окне и в документации.
- Своё состояние включения хранить в настройках Cactus. **Открытый вопрос:** читать ли
  `%AppData%\...\FCS_Extended.json`, чтобы унаследовать галочки пользователя. Скорее нет — файл
  чужой, формат может поменяться.
- **Сделано (этап 3), `node/extensions.ts`.**
  - Имя расширения для настроек: `mods/<папка>`, `workshop/<папка>` или полный путь папки, если мод
    лежит в другом месте. Показываемое имя — имя папки; у папки мастерской (она числовая) — имя
    первого `.mod` в ней.
  - По умолчанию берётся папка открытого мода (даже если самого `.mod` ещё нет) и папки его
    загруженных зависимостей. Выбор — `ExtensionChoice { auto?, enable?, disable? }`:
    `enable` добавляет чужие расширения, `disable` убирает, `auto: false` отключает набор по
    умолчанию. `loadModContext` принимает его в `options.extensions` (`false` — без расширений)
    и возвращает применённый список в `LoadedContext.extensions`.
  - Порядок слоёв — **как у FCS Extended, а не по `mods.cfg`**: папки `mods/` по имени без учёта
    регистра, потом мастерская по имени папки, потом папки «со стороны». Так номера значений
    enum, которым номер не задан явно, совпадают с FCS Extended. Но если Cactus применяет только
    часть расширений, такие номера всё равно могут отличаться — в своих расширениях писать
    значения с явным номером.
  - Папка самой игры расширением не считается. Расширение из одного `FCS_extended.json` (только
    DLL) попадает в список, но схему не меняет.
  - Чужой файл с галочками FCS Extended в `%AppData%` **не читаем** (открытый вопрос закрыт).
  - **Осталось на этап 4:** хранить выбор в настройках окна (для чистки JSON из настроек есть
    `normalizeExtensionChoice`). Окно сейчас строит схему у себя из текстов трёх ванильных файлов
    (`main/service.ts` → `renderer/src/project.ts`), расширения до него **не доходят** — нужно
    передавать слои (`readExtensionLayers`) или готовую схему. MCP в режиме «подключён к окну»
    берёт набор по умолчанию, а не выбор окна.

### 4.6. Регулярные выражения: .NET против JS
Патчи рассчитаны на .NET. Простые конструкции совпадают. Известные отличия: именованные группы
(`(?<name>…)` работает в обоих, `(?'name'…)` и `\A`/`\Z` — нет), флаги `(?i)` в начале (в JS
нет — придётся разбирать префикс), подстановки (`$1` одинаково; `$&`, `${name}` — следить).
Нерабочая регулярка = предупреждение с файлом и строкой, а не падение; остальные патчи применяются.
Покрыть тестами. Заранее описать список отличий в коде (на английском).

## 6. Риски и открытые вопросы

- Где настоящее определение `itemType` для новых типов (4.3) — первая вещь, которую проверить.
  **Закрыто:** в def-файлах его нет, номер в DLL; берём из комментария-подсказки, см. 4.3.
- Различия .NET/JS регулярок (4.6).
- Порядок обхода папок `EnumerateDirectories` в .NET не гарантирован (на NTFS на деле
  по алфавиту); в Cactus делаем по алфавиту и фиксируем это в тесте.
- Кодировка: FCS Extended пишет пропатченный текст в ASCII; мы читаем UTF-8. Для патчей с
  не-ASCII символами результат может отличаться, считаем это приемлемым.
- Невозможно проверить на «живых» модах из мастерской: ни у одного установленного нет этих
  файлов. Единственный реальный образец — примеры из kenshi-bridge.
- Дублирование значений enum из разных расширений: как именно ведёт себя `AddValue` в FCS при
  совпадении имени — не установлено. Берём «последний выигрывает» и пишем предупреждение.
- **Не проверено на настоящем FCS Extended (сделано по смыслу, 2026-11-15):** поле, заданное
  повторно в более позднем def-файле (у нас остаётся первое, предупреждение — если вид другой);
  склейка узлов layout с одинаковой подписью (у нас — дописывание); имена ванильных файлов, по
  которым ищется цель патча (считаем `fcs.def`, `fcs_enums.def`, `fcs_layout.def` в нижнем
  регистре, сравнение с учётом регистра). Настоящих образцов `*.def.patch` нет ни одного.
- Старые сообщения парсеров остались на русском, новые (про расширения) — на английском.
